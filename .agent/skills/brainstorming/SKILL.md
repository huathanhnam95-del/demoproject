# Resolve design uncertainty

Read the available context first. Identify the decision that prevents useful progress, not an arbitrary list of questions. Continue independent work while requesting missing information when the host supports it.

For each important uncertainty, distinguish a discoverable fact from a user preference or policy choice. Investigate facts directly. Ask concise questions only where the answer changes scope, behavior, risk or the deliverable. Existing authorization and settled decisions remain valid.

Compare a few viable approaches with concrete consequences. Recommend one based on the actual constraints, including retaining the current design when appropriate. Use examples, a sketch or a small prototype only when it resolves the uncertainty efficiently and is within scope.

## Optional design challenge

When the user asks to stress-test an idea, probe its assumptions, failure cases, data ownership, incentives and reversal cost. Follow consequential ambiguities to a useful answer; do not exhaustively interrogate every branch or force agreement on incidental details.

Summarize the selected direction, acceptance criteria and remaining uncertainties in the requested format. For substantial execution planning, use [writing-plans](../writing-plans/SKILL.md) when needed. No automatic document, commit, new worktree, agent dispatch or mode switch is part of brainstorming.

Stop when the design is sufficiently clear for the authorized next step. Respect actual project approval gates; do not invent a new gate for every creative or cosmetic change. [Provenance](SOURCE.md).
