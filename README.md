# Cursor AI repository

This repository contains the learner web application, CRM, Firebase Functions and separately packaged pronunciation services. Start with [`AGENTS.md`](AGENTS.md) for workspace process and protected product rules. The authoritative placement and dependency map is [`agent_docs/project_structure.md`](agent_docs/project_structure.md); [`docs/AGENTS.md`](docs/AGENTS.md) scopes documentation work.

## Structure governance

The machine-readable registry is [`scripts/structure/policy.json`](scripts/structure/policy.json). The checker is deliberately read-only and finite: it validates configured roots, declared task deltas, selected artifact classes, simple command declarations and registered generated-pair parity. It does not prove application behavior, semantic ownership, dynamic imports, transcript/pronunciation accuracy, audio quality, release readiness or remote branch protection. Existing findings are retained in the reviewed finite baseline; new occurrences are still reported.

Before coding, keep the task contract and before snapshot outside Git. The declaration names the actual owner or unresolved owner, create/modify/delete/rename paths, output destinations and effect classes, protected contracts, verification and exceptions. At completion, compare the real worktree/index delta and output history with that declaration.

## Supported commands and effects

Run these from the repository root:

| Command | Effect and scope |
| --- | --- |
| `npm run test:structure` | Runs Node's built-in test runner against synthetic fixtures and disposable OS-temporary repositories. It does not start the app, access the network or write repository files. |
| `node scripts/structure/check.cjs snapshot --contract <external-task-dir>/structure-contract.json --out <external-task-dir>/structure-before.json` | Reads the worktree/index and writes only the explicitly named external snapshot. |
| `npm run check:structure -- --base <resolved-base-sha> --contract <external-task-dir>/structure-contract.json --snapshot <external-task-dir>/structure-before.json --json` | Local declaration/output-history check. Requires both external inputs; local mode does not silently use a candidate declaration or missing snapshot. |
| `node scripts/structure/check.cjs check --ci --base <base-sha> --head <head-sha> --json` | CI committed-tree comparison. It does not receive or evaluate a human task declaration. |
| `node scripts/structure/check.cjs check --ci --full [--head <head-sha>] --json` | Explicit full-tree CI check against the fixed adoption baseline. It is not a release or semantic audit. |

Exit status `0` is pass with possible legacy notices, `1` is a structural violation, and `2` is invalid or missing input/schema. The workflow obtains only validated missing Git objects; the checker itself never fetches. No command above runs application tests, generators, browsers, Firebase, Cloud Run or deployment operations.

## Repository map

- `public/` is the Firebase Hosting root and served browser surface.
- `functions/` is the self-contained Firebase Functions package; shared server domain factories live in its domain home and local adapters live under `src/`.
- `backend/` contains separately packaged Python/audio services and their existing Docker/Cloud Build boundaries.
- `scripts/` contains declared generators, audits and operators; `scripts/structure/` contains this governance registry/checker.
- `tests/` contains domain and Chrome browser checks; `tests/fixtures/` contains deliberate sanitized fixtures.
- `docs/`, `agent_docs/`, `assets/` and `data/` retain their scoped documentation, authority, canonical-source and generated-data roles.
- `test-results/<task-id>/` is an explicitly declared ignored evidence destination; bulky retained evidence belongs in the external task directory or a declared retention class.

New CRM and practice placement, browser-global versus Node module boundaries, canonical/generated/evidence ownership, cleanup register semantics and the eight structural rules are maintained in [`agent_docs/project_structure.md`](agent_docs/project_structure.md). Do not duplicate that rulebook here.

## Verified release candidates

The supported release wrapper prepares and verifies a private candidate from an identified source commit before invoking Firebase. Hosting, Functions and full profiles retain their existing selectors. The deployment workflow accepts only a successful `RFIB Verify` push or manual dispatch from this repository's `main` branch, validates the originating `head_sha`, and checks out that exact commit before preparation.

The wrapper guarantee covers the selected source revision, the declared candidate inputs and repository-controlled preparation through the final surface comparison. It does not claim absolute immutability: another process or Firebase CLI packaging may still read or mutate files after that comparison, and generated bytes are not promised to be equivalent across separate CI jobs. The source SHA identifies what the deployment candidate starts from; it is not a cross-job artifact attestation.

Firebase hooks retain three states for direct invocations. With no wrapper context, the existing product-specific hook sequence runs and propagates failures. A complete valid wrapper context performs a read-only surface check. Any reserved context field that is present but empty, malformed or incomplete fails before generation or publication and never falls back to legacy generation.

Functions dotenv files are private recognized configuration inputs. The wrapper preserves the selected project ID or alias and equivalent configuration-directory resolution, stages applicable files opaquely when required, and keeps their raw contents out of Hosting, receipts, review artifacts and public logs. Missing, conflicting or unrepresentable configuration fails before publication; credentials and configstore files are never copied into a candidate.

Use the existing npm deployment aliases for ordinary local releases; they resolve the current `HEAD` when no source is specified. The explicit wrapper form is `node scripts/release/firebase-release.cjs hosting --sha <40-hex-sha> --project <firebase-id-or-alias> --firebase-cli <path-to-firebase.js> --non-interactive`, with `functions` and `full` profiles for their corresponding supported selectors. The wrapper accepts a Firebase project ID or configured alias string and reports actionable guidance for an unsupported numeric project number; the raw Firebase CLI remains available with its normal project-resolution behavior. The publication path resolves the pinned Firebase CLI 15.29.0 from the installed release module and executable used for that invocation rather than silently selecting a different global CLI. CI provisions it outside the checkout with `npm install --prefix "$RUNNER_TEMP/firebase-cli" --no-save --package-lock=false firebase-tools@15.29.0` and passes the package's `lib/bin/firebase.js` entrypoint explicitly.

A local candidate rejects modified tracked release inputs while allowing unrelated working changes to remain outside its source. Hosting preserves existing ignored media only when its provisioned published path is explicitly observed and verified; missing required inputs, unresolved LFS pointers and selected-source omissions fail before publication. These bounded checks do not classify every untracked file or establish whole-site content completeness. Standalone generators keep their existing wall-clock defaults, while release preparation passes one validated source-commit timestamp explicitly.
