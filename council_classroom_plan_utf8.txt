***

### Phase 1: The Blueprint (Feature Specification)

We will compartmentalize this system into three distinct domains: **Orchestration**, **Content Delivery**, and **Submission Pipeline**.

#### 1. Domain: Orchestration (Class Management)
This is the structural backbone. It governs relationships and access.

*   **Class Provisioning:**
    *   **Immutable Identity:** Every class generates a unique, alphanumeric UUID and a 6-character short-code (Join Code) for easy distribution.
    *   **Metadata Layer:** Title, Section, Subject, and Room.
    *   **State Management:** Active, Archived, or Deleted (Soft Delete).
*   **Enrollment Protocol (RBAC):**
    *   **Instructor Role:** Inherits permissions to CREATE, UPDATE, and DELETE content.
    *   **Student Role:** Inherits permissions to READ content and CREATE submissions.
    *   **The Handshake:** Students join via the 6-character short-code. This reduces admin overhead by offloading enrollment effort to the user.

#### 2. Domain: Content Delivery (The Stream)
The central communication hub. We differentiate between passive and active data.

*   **Announcements (Passive):**
    *   Rich-text stream items visible to all enrolled entities.
    *   Support for external links and attachment metadata.
*   **Classwork (Active):**
    *   **The Artifact:** Contains instructions, due dates, point values, and reference materials.
    *   **State Tracking:** Draft (Invisible), Scheduled (Time-gated), Published (Live).
    *   **Versioning:** Edit history tracking to prevent "gaslighting" on assignment parameters.

#### 3. Domain: Submission Pipeline (The Interaction)
The highest load vector. This requires decoupled storage handling.

*   **Student Workflow:**
    *   **The Envelope:** A submission object tied to a specific User and specific Classwork ID.
    *   **The Payload:** Support for file uploads (PDF, Docx, IMG). *Critical: Files are never stored in the database.*
    *   **Status Flags:** `Assigned` -> `Missing` (Auto-triggered by date) -> `Turned In` -> `Returned`.
*   **Instructor Workflow:**
    *   **Review Interface:** Aggregated view of submissions filtered by Classwork ID.

***

### Phase 2: Architectural Data Model (Entity Relations)

To ensure scalability, the database schema must favor efficient querying of relationships.

1.  **`Classrooms` Table:** The root entity.
2.  **`Enrollments` (Junction Table):**
    *   Links `UserID` to `ClassroomID`.
    *   Stores `Role` (Student/Teacher).
    *   *Why:* Allows a user to be a Teacher in one class and a Student in another without schema friction.
3.  **`StreamItems` (Polymorphic):**
    *   Stores Announcements and Assignments.
    *   Indexed by `ClassroomID` and `CreatedAt` for rapid timeline rendering.
4.  **`Attachments` (The Pointer System):**
    *   Stores file metadata (Name, Size, MIME Type) and the **Object Storage URL (S3)**.
    *   *Never* store binary data in your SQL instance.

***

### Phase 3: Scalability & Best Practices

1.  **Storage Decoupling:**
    *   Use AWS S3, Google Cloud Storage, or Azure Blob for all classworks and submissions.
    *   The CRM database only holds the *reference key* to the file. This keeps the database lean and fast.
2.  **Asynchronous Processing:**
    *   When a teacher posts an assignment to 5,000 students, do not trigger 5,000 notifications in the main thread.
    *   Push this event to a Message Queue (RabbitMQ/Redis/SQS) to handle notifications in the background.
3.  **Pagination Strategy:**
    *   The "Stream" must use cursor-based pagination. Do not load "All Classwork" at once. Load the most recent 20 items.

*   **Admins** post to the Stream.
*   **Students** react to the Stream (via submissions).

#### 1. The Container (Class Management)
*   **UX Focus:** Minimalist Card Interface.
*   **Admin Action:**
    *   **Create Class:** A simple modal requiring only `Name`, `Subject/Category`, and `Description`.

*   **Student Action:**
    *   **Join Class:** A prominent "Join" button on their dashboard. They enter the code, and the relationship is instantly bonded. This removes the administrative burden of manually adding users to classes.

#### 2. The Instructor Suite (Admin/CRM View)
The Admin view is the command center. It requires two distinct creation flows that feed into the same UI list.

*   **The Stream View:** A vertical list of cards. Newest items on top.
*   **Action 1: Create Announcement:**
    *   **Fields:** Text Body, Attachments (PDF/Images).
    *   **UX:** Simple text editor. No status tracking needed.
*   **Action 2: Create Assignment:**
    *   **Fields:** Title, Instructions, Due Date/Time, Attachments.
    *   **Status Dashboard:** On the assignment card, the Admin sees a mini-dashboard: *"3 Assigned | 0 Turned In."* clicking this opens the submission review panel.

#### 3. The Student Portal (Client View)
Simplicity is paramount here. The student should never question "What do I do next?"

*   **The Dashboard:** Shows joined classes as cards.
*   **The To-Do List (UX Priority):** A dedicated sidebar or tab showing *only* assignments with pending status.
*   **The Submission Flow:**
    *   Student clicks an Assignment.
    *   **State 1 (Pending):** Sees instructions. A drag-and-drop zone for files (or text input). Button says "Mark as Done" or "Submit."
    *   **State 2 (Submitted):** UI locks. Button changes to "Unsubmit" (optional, for corrections) or "Submitted".
    *   **State 3 (Returned/Graded):** Admin feedback is visible.

#### 4. The Data & State Logic
To ensure the CRM remains fast, we will utilize a flat status architecture for submissions.

*   **Assignment Lifecycle:** `Draft` -> `Published` -> `Archived`.
*   **Submission Lifecycle:** `Assigned` (Default) -> `Missing` (Post-due date) -> `Turned In` -> `Returned/Reviewed`.
