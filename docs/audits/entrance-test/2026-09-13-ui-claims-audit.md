# Entrance Test UI: verified findings and overhaul recommendation

Date: September 13, 2026 (Vietnam Time). Status: audit completed; redesign proposed, not implemented or approved.

**Subsequent user direction, September 13:** this is a UI demo and the answer-prefill shortcut is intentional. Preserve demo helpers and defer answer-key isolation to the later live-release package; the exposure finding below is not a blocker for demo work. Try the Projects page's Noto Sans font. The [demo overhaul handoff](../../plans/2026-09-13-entrance-test-ui-demo-overhaul-handoff.md) supersedes the original priority and typography recommendations below.

The report is useful design research, but its **“Complete & Audited” production specification overstates the evidence**. Its main rating calculations are reproducible. Several descriptions of the current UI are incorrect, its screen comparison reintroduces the sampling imbalance it identifies, and it omits substantial implementation and assessment-integrity requirements.

**Recommended direction:** one calm, accessible assessment interface using the production session/content contracts, inline answers, clear instructions, visible progress, reliable draft and recording recovery, and one final review. Use the lab as a design reference. Do not promote its standalone engine into production.

## Important omissions and reproduced defects

1. **Public answer-key exposure needs first attention.** The unauthenticated Hosting lab contains the real question content, derives correct answers from its raw strings, and exposes a QA prefill control. Its embedded answers achieve **45/45 against the current local canonical scorer**. This is not a live scored submission. All 13 question texts match canonical content after normalizing quotation marks; seven match exactly. The public payload itself is the exposure, so hiding a QA button or adding a client-side login check would not resolve it. Use synthetic content for public demos; if real content is needed for staff evaluation, serve it behind authorization. Since current items are exposed, academic leadership should decide whether to replace them before relying on future diagnostic results.
2. **“Saved” does not mean the same thing across versions.** Lab text and flags survive reload, but recorded audio does not. A recorded take became zero audio elements and zero re-record controls after reload. Lab saving swallows storage errors and can still present a saved timestamp. Production saves responses after each question is submitted; changing a select and reloading before Submit loses that edit. Its progress API fallback can remain local-only. Continuous autosave is a new behavior requiring truthful local/sync/error states.
3. **Review changes the submission model.** In the production-source browser flow, completing the final listening question invoked `/submit` directly and rendered Done without a whole-test review. Speaking uploads happen separately before final submission. A new review screen must track uploaded recordings and pending changes; a view-only review grid is insufficient.
4. **Resume currently uses an ordinal `stepIndex`.** Adding a mic step or changing section introductions can reinterpret old drafts as a different question. Use stable question IDs and explicit migration/version handling for the UI resume state. Preserve test version, blank IDs, randomized option order, scoring, learner-link behavior, and CRM integration.
5. **Keyboard and mobile behavior need explicit repairs.** After a keyboard selection, the lab rerenders the application and focus returns to `BODY`. Empty inline blank buttons lack an explicit accessible label. The listening seek control is a `DIV` with no role, name, or tab stop. At 390px, automatic scrolling to the active answer rail pushes instructions and the beginning of the passage above the viewport; at 360px, document width measured 377px. No horizontal overflow was measured in the other captured states; this was not a comprehensive accessibility audit.
6. **Review needs useful state semantics.** The current empty review grid floods the page with red error cards. Use neutral not-started states, explicit partial counts, and clearly labeled recording readiness. Completion means all blanks answered or a recording durably available; it does not mean correctness. A response receipt must follow server acknowledgement, and any teacher/contact promise must reflect an actual supported workflow.

## Proposed direction and sequence

Three approaches are available:

| Approach | Benefit | Limitation |
|---|---|---|
| Restyle the sequential production UI | Lowest integration scope; improves typography, hierarchy and visual density quickly. | Leaves navigation, question-only saving and final review problems unresolved. |
| **Build one revised candidate on production contracts — recommended** | Combines calmer visuals with reliable test behavior; preserves canonical content and scoring ownership. | Requires deliberate draft, recording, navigation, and resume design. |
| Promote the standalone lab/hybrid specification directly | Fastest route to something resembling the report. | Carries exposed keys, demo shortcuts, simulated submission, in-memory audio, and keyboard defects into the delivery system. |

### 1. Contain exposure and define the product contract

Prepare a bounded change replacing public demo content with synthetic questions or moving real content behind server authorization. Any production publication still needs explicit deployment authorization. Retain evaluator ratings with their existing source context.

Separate assessment policy from styling. Recommended initial policy is to preserve the current untimed, read-aloud assessment and retry behavior; keep Vietnamese guidance available. Do not add a free-response task, countdown, retake cap, or a new playback-speed rule under a UI overhaul. Decide the default interface language, navigation permissions, retake policy, and mic-check requirement with the academic owner before implementation. Unlimited retries within a current prompt and free revisiting of earlier prompts are distinct decisions.

Define progress as **13 groups / 45 written blanks / 3 recordings**. For a passage, show answered blanks (for example, 2/4) and whether the group is partial. Avoid using “13 Questions” in a way that conceals the number of responses expected.

### 2. Make one complete, reviewable candidate

- **Shell and type:** white or subtly neutral reading surface, restrained blue action color, Be Vietnam Pro for controls and numerals, with `font-variant-numeric: tabular-nums` where needed. Test Literata and Source Serif 4 on the same long passages before choosing. Start around 18–20px passage text and 16px semibold instructions, with adjustable text size. Those are starting design values, not findings. Use open sections and dividers instead of nested cards.
- **Intro:** short purpose, four section summaries, honest save/retry guidance and one start action. Remove redundant eyebrows. Identify the three speaking tasks as read aloud.
- **Mic check and speaking:** input status plus a short record/playback check, retry/help path, elapsed recording timer, a clear stop control, playback and replacement of the take. Preserve the production `AudioDspPipeline` handling and existing scoring contract. Define local recording, processing, upload, uploaded, failure, and replacement states before describing a take as saved. Three seconds is not yet a justified hard gate.
- **Vocabulary/grammar:** inline controls at each blank. Start with styled native `<select>` controls, which already exist in production. This matches the requested familiar interaction with less custom keyboard/focus work. Introduce a custom combobox only if browser trials demonstrate a concrete need. Reserve width sensibly and test reflow with long options. Use the same neutral selected styling for vocabulary, grammar and listening.
- **Listening:** simple accessible native controls or an equivalently accessible play/seek/time control. Remove the decorative waveform. Keep replay/speed behavior explicit and consistent with approved assessment policy.
- **Navigation:** desktop part tabs and numbered group navigation with partial/complete/flagged labels. A selected passage can expose its blank progress without confusing blank numbers with group numbers. On mobile, use an active-part summary, previous/next controls and a touch-operated question overview. Do not cram every desktop label into a fixed 60px footer. Reserve space for sticky controls and the software keyboard.
- **Review and receipt:** group by section; make missing answers and recording problems actionable; offer jump-to-first-missing and one clearly labeled final submission action. Show pending/saving/failed states and recover from interrupted submission. Show Done only after acknowledged submission, with a supported next step.

Use one session/draft owner and reusable components; skin styling must not duplicate question data, business rules, or API code. Keep server-only answers out of the browser payload. Name progress and save states consistently across the footer, review screen, and restored session.

The interaction references are valid inspirations: Pearson documents dropdown completion and reading around the blank ([official reading format](https://www.pearsonpte.com/pte-academic/test-format/reading/)); IDP documents bottom navigation for IELTS on computer ([official explanation](https://ielts.idp.com/ecuador/prepare/article-how-computer-delivered-ielts-works)). Neither establishes that copying a precise layout, color or exam rule will improve this placement test. Make keyboard access, reflow, focus visibility and non-color status labels part of acceptance using [WCAG 2.2](https://www.w3.org/TR/WCAG22/).

### 3. Evaluate the candidate through tasks, then implement and release separately

Use the same representative tasks with actual candidate-level users, including lower-proficiency and mobile users: complete/edit a cloze passage, record/replay/replace audio, navigate to an incomplete item, recover after reload, and submit. Rotate comparison order and record UI revision, viewport, font pair, task completion, wrong-control actions, navigation/scrolling burden, assistance needed, and any lost response. Keep staff aesthetic ratings as a secondary signal. A small formative round can uncover defects; do not present it as statistical proof of superiority.

Acceptance before rollout:

1. Public assets and session responses contain no answer keys or QA shortcuts.
2. Edits, flags and confirmed recordings restore correctly after navigation/reload; old drafts resume on the intended question. Saving failures remain visible and never claim a remote save.
3. The complete flow has one final review and acknowledged submission; duplicate clicks, failed uploads and interrupted responses cannot silently lose answers or produce a false receipt.
4. All answer/navigation/audio controls work by keyboard with stable focus and accessible names. Check Chrome at desktop, 768px, 390px, 360px and 320px, plus 200%/400% zoom and mobile keyboard layout. Font loading failure and Vietnamese accents remain readable.
5. Canonical question IDs, options, content, DSP/scoring contracts and CRM result/link behavior remain intact; focused regression tests and a settled-candidate browser pass verify them. Authentication plans reference `C:/Cursor AI/.local/browser-test-credentials.md`, without copying credentials.
6. Live rollout uses a separately approved, isolated candidate and verifies actual deployed assets and a controlled live attempt. This audit's synthetic API checks do not establish backend release readiness.

Implementation remains on the default Light route unless the user changes it. Proposed implementation lineup is Astra Medium root, Standard speed, with no subagents; confirm that lineup when beginning the new implementation project. No `implementation_plan.md` was created or changed by this audit.
