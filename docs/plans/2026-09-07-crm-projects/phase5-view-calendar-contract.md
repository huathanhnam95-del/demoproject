## Boundaries and design

Keep canonical tasks, project membership, typed columns, operation IDs, history and revisions authoritative. Add read projections and focused services; do not create independent Kanban/calendar copies of tasks. Preserve Phase1 administration, Phase3 board interactions and Phase4 discussion/recovery/account fences. Use AstraMedium for substantial implementation, at most two concurrent coders with disjoint ownership, isolated capsules and no child agents. Root reviews actual source and artifacts.

1. A coherent authorized snapshot supplies all view projections. Reuse query-service readSnapshot, effective ancestry, normalized filters and existing bounded project limits (20,000 tasks/1,000 sections/200 columns). Shared filters: section, status, accountable owner, assignee, title and date range. Dates use inclusive interval overlap for tasks with dates; define undated handling explicitly. Board context ancestors may be shown but must be labelled context and excluded from matching totals. Filters must survive switching Board/Kanban/Timeline/Calendar/Charts within the same actor/project.
2. Return full matching totals and active-leaf aggregates independently from displayed pages. A leaf has no effective-active child in the full project, not merely in the current filter/page. Charts show status, accountable owner and completion on this labelled basis, including unassigned. Parent progress and min/max descendant spans are derived from active descendant leaves, clearly distinct from stored parent status/dates. Never persist summaries back into tasks.
3. Paginate view rows with bounded opaque actor/project/filter/snapshot-bound cursors (maximum200/page), or reuse an existing equivalent safe query contract. Never silently stop at500 records or render thousands of DOM cards. Provide explicit Load more/visible range and full counts. No unbounded collection reads or browser-derived full-population chart totals.
4. Kanban status changes and timeline/calendar date edits use the existing canonical command boundary and current revisions. Provide real keyboard-accessible controls. Clicking a task identifies the same stable task/details/discussion. Retain board drag/keyboard behavior. Dates are date-only values; avoid timezone-induced day shifts.

## Dependencies and scheduling

5. Finish-to-start dependencies are same-project directed edges. Use a dedicated command/read service (or strictly validated task field), current role/ancestry/revision fences, immutable operation replay and complete graph cycle checks. Reject self/cross-project/duplicate edges and cycles atomically. Archived/missing dependency endpoints are visible warnings/tombstones without resurrecting them. Adding an edge never moves dates.
6. Expose missing dates and predecessor-finish/successor-start conflicts. Explicit Phase5 date/schedule suggestions produce a concrete preview of old/new dates, affected task IDs, working/nonworking dates, calendar/feed versions and warnings. Apply requires the exact preview intent plus fresh task/calendar/dependency fences. Concurrent calendar/task/dependency changes reject stale preview. No silent downstream shifts. Ordinary deliberate manual task edits remain canonical; recommendations and calendar synchronization never write schedules automatically.

## Organization calendar

7. Reuse existing organization calendar administration and authorization. Extend full-day leave to inclusive start/end ranges while preserving legacy single `date` records and tests. Whole team and Specific person scopes remain explicit. Validate real dates, bounded ranges, eligible people and revision conflicts. Preserve historical/manual entries when verified holiday data changes.
8. Calculate task working days from the accountable owner's calendar; unassigned uses the organization calendar. Other assignee leave creates a warning, never silently changes the accountable-owner schedule. Specific-person/whole-team leave is nonworking. Approved adopted working swaps may override an ordinary weekly-rest day but never erase a personal leave or statutory holiday. Preserve the reason/provenance of each nonworking day.
9. Member-facing calendar reads require current project access and disclose only relevant project-member calendar availability, not unrelated staff IDs, private labels or the entire admin configuration. Admin configuration endpoints retain their existing independent admin fence.
10. Curated versioned holiday data is read/merged with manual configuration, never fetched as unverified scraped dates during ordinary scheduling. A newer bundled verified feed takes effect in the effective calendar without overwriting manual entries or changing task dates. Return feed version, verifiedAt, source URLs, scope and status. Show coverage/unresolved choices explicitly; do not call a proposal a holiday or promise an official API.

## CRM references

11. A dedicated task-links subcollection/service avoids raw link leakage through generic task query/command/history serializers. Writes return task/revision/operation identity only; reads resolve current CRM authority every time, including after replay/revocation. Strict allowed types lead/student/classroom, safe IDs, bounded unique links, server-derived labels. Unknown/deleted/unauthorized references are omitted/redacted. Never trust caller labels.
12. Existing CRM routes currently use an independent admin gate, not Projects membership. Functions reads current users/{uid}.isAdmin; local middleware currently uses configured ADMIN_EMAIL. Inject explicit host-specific CRM authorization callbacks, preserving each existing boundary and current verified Auth. Do not substitute Projects Owner, workforce administrator, teacher, claims-only admin or local email shortcuts in production. Reuse the existing resolveLinkedRecordAccess seam for project links where appropriate, retaining deny-by-default when uninjected.
13. UI uses an authorized record picker/lookup and canonical name, not a raw unauthorized reference dump. Project members without CRM permission see no IDs/names/details from stored links. If no independent CRM access, link editing is unavailable. Existing record navigation remains subject to its original CRM gate.

### Fixed endpoint/DTO capsule for parallel workers

All paths below are relative to `/api/projects`; preserve the admin alias and existing response envelope (`success:true` plus named properties). Root approval is required before workers change this shared interface; routine internal choices remain theirs.

- `GET /:projectId/views?filters=<JSON>&pageSize=200&cursor=...`: returns `{ project, membership, tasks, nextCursor, hasMore, matchingTaskCount, aggregates, aggregateBasis, calendar, linkAccess, snapshotDigest }`. `tasks` are safe canonical task DTOs with `id`, `pathIds`, `ancestorTitles`, `contextOnly:false`, `derived:{activeLeafCount,completedLeafCount,completionPercent,startDate,dueDate}`, `predecessorTaskIds`, `dependencyWarnings`, `calendarWarnings`. Aggregates include `activeLeafTaskCount`, `completedLeafTaskCount`, `completionPercent`, `byStatus`, `byOwnerUid` (explicit unassigned key). `calendar` is limited summary `{timezone,revision,feedVersion,coverage,requiresConfiguration}`; `linkAccess.canManage` reflects independent CRM permission. No CRM link IDs/names in this projection. Filtered task pages include matches; ancestors for context belong to board query mode below, not totals.
- Extend existing `GET /:projectId/tasks` query with optional `includeAncestorContext=true`. For filtered Board mode, evaluate shared data filters over the full effective project, add necessary ancestor IDs, then apply root/direct-child branch scope and pagination. Return `contextOnly` on nonmatching ancestors. Existing calls with no option retain their established semantics. Shared field filtering/overlap implementation must be reused rather than drifting between the two endpoints.
- `PATCH /:projectId/tasks/:taskId/dependencies`: `{operationId,expectedRevision,expectedStructureRevision,predecessorTaskIds}` → canonical minimal result with task ID/revision. Dependencies are included in authorized view DTOs; no task copies or date moves.
- `GET /:projectId/calendar?fromDate=YYYY-MM-DD&toDate=YYYY-MM-DD`: bounded range (maximum366 days), returns `{calendar:{timezone,revision,feedVersion,coverage,requiresConfiguration,days}}`; each day has date and relevant organization/member availability and reason provenance. No unrelated staff records/labels. `GET/PATCH /calendar` remain admin configuration, extended with inclusive-range leaves and `holidayChoices` keyed by year. Choices: `tetScheme` (`before1_after3`, `before2_after2`, `before3_after1`), `nationalDayAdjacent` (`before` or `after`), `adoptPublicSectorSwaps` boolean. Absent choices are explicitly unresolved, not silently selected. Existing single-date leaves remain compatible.
- `POST /:projectId/schedule-preview`: `{taskId,expectedRevision,startDate,dueDate}` → `{preview:{token,taskId,before,after,workingDayCount,nonWorkingDays,warnings,canApply,calendarRevision,feedVersion}}`. Preview storage/token is actor/project/date/revision bound, bounded and expiring. `POST /:projectId/schedule-apply`: `{operationId,previewToken}` → canonical minimal task/revision result. Recheck task/calendar/feed/dependency state atomically where applicable. Invalid/uncertain computations must not be presented as confirmed.
- `GET /:projectId/tasks/:taskId/links` → `{links:[{type,recordId,label,href}],canManage}` after independent permission. `PATCH` same path accepts `{operationId,expectedRevision,links:[{type,recordId}]}` and returns only canonical minimal task/revision identity. `GET /:projectId/crm-link-options?type=lead|student|classroom&query=...&limit=25` returns `{options:[{type,recordId,label}]}` with bounded authorized lookup, not raw legacy objects. Link read/write/replay must recheck CRM permission. Denied options return no metadata with an explicit authorization response.

Frontend renders Board/Kanban/Timeline/Calendar/Charts as views in the existing workspace, with one shared filter bar and one common task detail/discussion area. A new `views.js` controller may coordinate them. Board exposes bounded `setFilters` and stable-task selection methods as needed; changing view must not create or copy tasks. Use native controls and flat BEL layout; no nested card stacks or paid libraries. Admin calendar UI extends existing `access.js` controls instead of duplicating organization settings. Every asynchronous view/preview/lookup callback is fenced by captured current UID/project and request generation.

Require current Projects Owner and independent CRM authorization for writes, and current membership plus independent CRM authorization for resolved reads. Reuse the same authorized options endpoint and resolver as task links. Provide a clearly labelled project-level picker/read/remove/save surface, available without selecting a task. Do not duplicate the existing GET route.

Keep new raw project references outside generic project query/command/history payloads (a dedicated project-links record/subcollection is preferred). Resolve legacy stored project references through the same current permission filter, with explicit replacement semantics when a new link record exists. Project command replay, generic project edits, undo and recovery must not disclose legacy or new reference IDs/names to an unauthorized actor. Verify project-level persistence/reload, removal, revocation, forged labels, absent records and replay alongside task-level coverage.
