# Projects: independent desktop interaction and performance audit

Audit date: September 26, 2026. Owner: Codex task `01a0db13-02d2-7ef2-be7f-d57bc85ea945`.

This extends [handoff-plan.md](handoff-plan.md). Sections 1–7 preserve the original audit and proposed work; sections 8–9 record the subsequently authorized implementation and its evidence. **Desktop only: no mobile development, design, audit, or test coverage.** No dependencies, tracker rows, live data or releases were changed by this task.

## 1. Main assessment

The original plan is useful for the table, task drawer and main views, but it is not a complete acceptance plan for the business workflow. Its highest-risk omissions are retained work, truthful counts, task movement, notification navigation, automation drafts and route changes during voice use. Address those before spending the whole budget on spacing and styling.

The table is already reasonably efficient in the measured synthetic scrolling case. Avoid rewriting its rendering system without evidence. The larger performance opportunity is unnecessary reads and redraws, including backend work hidden behind small paginated responses. Production latency, actual database cost and long-session behavior remain unmeasured.

Three important corrections to the old plan:

1. Switching between settled non-Calendar views already reuses data. A fresh Chrome sequence made **zero new requests** for Table → Kanban → Charts → Gantt; Calendar then made two, returning to Table made zero, and the subsequent Kanban made one. This is a query-boundary and invalidation problem, not universally a fetch on every view switch.
2. The inspected dates preview does **not** shift the submitted dates. It checks working-day configuration, warnings, dependencies, revisions and a snapshot consistency token. Simplify the interface while preserving those protections.
3. Calendar fetches tasks whose date intervals overlap the month, but renders them on their due date/start fallback. A spanning task can be counted yet absent from the grid. The original description of a purely due-date calendar was incomplete.

### A. Protect business work and make the displayed state truthful

**D01 · P1 · Automation drafts disappear on project change — Chrome + Source.**

`automations.js:29–35` resets both draft and pending request on selection change; `:115–135` holds the exact body needed to retry an interrupted save. In Chrome, a ready Owner controller had `draft=true`, `dirty=true`; changing A → B → A left `draft=false`. Original request identity matters for server deduplication (`automation/rule-service.js:26–31`). Retain drafts and unresolved requests per account/project, or give deliberate navigation a Save/Discard/Stay choice. An uncertain server result must be reconciled before creating a replacement operation. Acceptance: return to the draft; retry an interrupted save using the original identity; changing account exposes no previous account's content.

**D02 · P1 · A subtask's Move dialog defaults to Root task — Chrome.**

`board.js:2883–2893` never selects the current parent in the destination picker. Chrome confirmed an existing child of `p0` opens with value `""` / Root task even though `p0` is an available option. Pressing Move can therefore promote it accidentally. Initialize its actual parent, make an unchanged destination a no-op, and explain intentional moves out of a parent. Acceptance: reopen a nested task, submit unchanged, then explicitly move to Root; descendants and section identity remain correct.

**D03 · P1 · Calendar totals leak into Table as whole-project totals — Chrome.**

`views.js:172–180` marks the response stale when leaving Calendar for Table but retains it; `:520–525` relabels it. In the date-aware synthetic fixture, Table initially showed 15 tasks, Calendar showed 14, then Table showed 14 and its accessible description said “in the full project.” Never relabel a response for a different query. Either use valid board totals, restore the matching full-project response, or temporarily show a clearly pending summary. Acceptance: months, filters, no matches and paged results all retain honest count scope.

**D04 · P1 · Stop Projects voice work on route departure — Check, not reproduced.**

`crm-admin.js:2030–2043` builds assistant context/readiness without the current CRM page; `:2070–2071` keeps synchronization until pagehide. `workspace.js:258` closes dialogs on navigation, while `assistant.js:20` treats unchanged project context as current. This appears to permit voice to remain active after navigating to another CRM page. Verify with a stubbed transport and intercepted writes, not paid/live voice commands. Require explicit microphone/transport shutdown and rejection of late transcript/confirmation results on route departure, account loss or revoked access. Retain safe draft text, and require deliberate voice restart on return. Preserve the existing voice-confirmation requirement.

**D05 · P1 · Discussion edit conflicts lose the attempted text — Source.**

`discussion.js:430–448` obtains an edit through a native prompt; `:355–365` removes its retry records on a known client error, reloads and asks the user to edit again. A concurrent edit can erase a long attempted correction. Keep the attempted text separately, show current and attempted versions, and require deliberate reapply against the fresh revision. Acceptance: conflict, cancel and explicit reapply; no silent overwrite and no lost text. A small in-place editor would also make multiline editing and recovery more usable than `window.prompt`.

### B. Repair everyday table, drawer and keyboard interactions

**D06 · P2 · Changing date-picker month/year drops focus — Chrome for Next month; Source for selects.** `date-picker.js:105`, `:168–174`, `:210–218` replace the focused controls. Chrome's active element became BODY after Next month. Keep controls mounted or restore the initiating control/logical enabled day. Keyboard navigation, month/year choice, Escape and focus return must work without restarting from the page.

**D07 · P2 · Show more drops keyboard focus — Chrome.** Kanban's Show more handler (`views.js:1260–1264`) rebuilds the view (`:529`). Enter on Show more left focus on BODY. Restore focus to the next meaningful item or a stable load-more control, preserve column scroll and announce the added count. Audit the same redraw pattern for Calendar disclosures, Gantt controls, Charts and remote updates; those related cases are not yet reproduced.

**D08 · P2 · Default section headers have no keyboard route to resize/edit — Chrome + Source.** The shared header is hidden (`board.js:181`); replacement separators have `tabindex=-1` (`:2109`) and row navigation skips header rows (`:3023–3027`). Chrome confirmed hidden shared header, untabbable local handles and edit buttons, and missing width accessibility values. Add a deliberate header keyboard route; keep numeric widths in Columns as an alternative. Arrow resize and Escape must retain focus and announce current/minimum/maximum widths.

**D09 · P2 · Width/visibility preferences can freeze shared column order — Source + module calculation.** `table-layout.js:12–18,85` saves a complete normalized order; `column-model.js:24–36` prioritizes it; `board.js:4018–4030` changes canonical order without reconciling that personal order. After one width/visibility save, a shared drag can succeed while the screen keeps the old order. Decide and label whether drag ordering is personal or shared, then make the behavior consistent. Acceptance: resize, reorder two custom columns, reopen; a second member sees the intended shared/personal outcome. Do not rewrite preferences or discard hidden columns wholesale.

**D10 · P2 · Failed destination loading strands Move — Source.** `board.js:2889–2892` disables Move, then returns on a null append index; `:4051–4053` returns null after failed branch loading. Restore the button in the still-current dialog, retain the destination and display Retry. Verify one failed read followed by successful retry, plus navigation while the read is delayed.

**D11 · P2 · Overdue dates have no V2 table signal — Chrome.** `board.js:1979` sets `dState='none'` for V2, making the overdue CSS at `crm-projects-v2.css:544` unreachable. A synthetic unfinished task due September 2 still rendered `data-due-state="none"` on September 26. Restore the intended deadline state, with text/icon as well as color. Compare overdue open, future open, completed and undated tasks in Table and other views.

**D12 · P2 · Retained date draft and visible date cell disagree — Chrome.** `board.js:2808` stores a `dates` draft, while `:1955–1958,1992` render individual start/due values. Chrome retained a November 25 due date after dismissal but the cell still showed October 1; reopening revealed November 25. Clearly show either draft values with Unsaved or saved values with a discoverable retained-draft indication. Apply failure and conflict must use the same understandable convention.

**D13 · P2 · Drawer redesign must include reading, editing and scaling — Chrome visual observation.** Retain plan A, but include title wrapping, property alignment, internal scroll, keyboard close/focus return, custom field types, missing values, validation and saved/unsaved/error feedback. The 150% text screenshot enlarges labels/pills while some native text fields remain visually small. Verify computed sizes during implementation. Use an editable heading and a flat property list; avoid a second form/card inside the drawer. Keep dependency/history/copy-ID functions reachable. Do not remove working-day uncertainty by presenting an invented count.

### C. Make every view complete, understandable and economical

**D14 · P1 · Calendar's count, grid and task list describe different things — Chrome + Source.** Server overlap filtering is `domain/query-service.js:95–100`; due-date placement is `views.js:684–689`. Chrome showed 300 overlapping tasks with an empty September grid because they finished in October. The date-aware 15-task fixture confirmed the same behavior independently. **The user selected bars spanning the task's working period during this audit.** Plan start-to-due bars split across week rows, with an accessible overflow list. Preserve calendar dates across weekends/holidays. Shade organization-level non-working days; keep authoritative owner/task-specific availability and warnings distinct rather than implying every task shares the background calendar. Show continuation at month/week boundaries. A task with only one date uses a one-day marker. This settles the design direction; implementation has not started.

**D15 · P2 · Calendar overflow and paging hide work — Source.** `views.js:690` emits a non-clickable `+N more`; `:691` calls the current response page “All tasks active…”. The normal API page is at most 200, and paging replaces it (`:818,1247–1248`). Make overflow open a keyboard-accessible list, qualify counts and page scope, and give a reliable route to every matching task. Do not adopt an arbitrary three-bars-per-week cap without an overflow and completeness design. Decide whether the control appends results or navigates pages; label it accordingly.

**D16 · P2 · Calendar Today/month uses UTC instead of the intended business date — Source.** `views.js:27,677` and its Today handler use `toISOString()`. Before 07:00 Vietnam time this can select yesterday or the previous month while the date picker uses local dates. Choose the project/business timezone explicitly and use it consistently in Calendar, overdue status and readable timestamps. Verify a fixed time near Vietnam midnight and a month boundary; do not rely on the test machine's timezone.

**D17 · P1 performance work · Avoid duplicate expensive reads before adding caches — Source + request observations.** `/views` reads a canonical project snapshot first (`view-calendar-service.js:56–71`; `domain/query-service.js:144–174,233–300`), then resolves hierarchy, filtering, totals and paging. Limits include 20,000 tasks, 1,000 sections and 200 columns. A 200-task response is not evidence of only 200 database reads. Next-page requests repeat snapshot work; cursor creation can also write a query record (`:348–354`). Remove the Table's avoidable summary read or load authoritative summary information separately without substituting incomplete root-task counts for leaf totals. Profile server duration/read counts before a separate backend redesign; this audit did not measure production query cost.

**D18 · P2 · Query caching needs an explicit correctness contract — Source.** Existing in-flight deduplication (`views.js:756–763`) and six-entry Calendar metadata cache (`:725–738`) should be preserved. If adding settled `/views` reuse, key it by actor, project, normalized query/date intersection, page/cursor, supported sort and authority/change generation. Clear/fence on access/account/project/lifecycle changes, local/remote changes, explicit refresh and invalid cursors. Preserve request sequence guards and revision-floor reconciliation. Never store failure as current data or mutate reusable cached response objects in place. Cursors expire after 15 minutes and snapshot changes (`query-service.js:231–235`). Bound cache size and measure memory over repeated project switches.

**D19 · P2 · Loading and redraws should preserve orientation — Source + D07 reproduction.** Non-Calendar empty response renders “Choose a project or refresh” while a valid request may be in progress (`views.js:526–527`). Use distinct loading, no matches, no tasks, denied, offline and failed states; retain stable geometry and provide local Retry. Keep useful prior data visibly marked as updating only while authority remains valid. Review Gantt current-page rendering (`:540–546`) and all-owner Charts rendering (`:558–570`) separately; neither is proven cheap by Kanban batching. Preserve focused controls, scroll, expanded lists, pending drag and selection on unrelated updates.

**D20 · P2 · Returning to Projects refreshes settings dependencies too — Source.** `crm-admin.js:6201–6204` calls access refresh; `access.js:511–540` loads people, Calendar, allowance, projects and then memberships for an admin. Measure warm returns and consider deferring settings-only data until opened. Permission revalidation remains mandatory; cached content must not restore editing on stale access. Observer acceptance should prohibit newly scheduled `/changes` requests while away/hidden, while allowing an already-started request to settle safely.

**D21 · P2, separate package · Lazy loading needs a lifecycle design.** Keep original G separate. Classic script order, one initialization promise, loading/retry UI, route departure during load, direct task links, account changes and disposal all matter (`crm-admin.html:3236–3252,3295–3301`; `presentation/entry.js:20–38`). Coordinate the existing HTML owner. Measure current raw/compressed assets again at implementation; the earlier size estimate is not a current release manifest.

### E. Project creation and settings supplement

**D29 · P1 · Project creation has no in-flight guard — Source.** `board.js:3260–3276` issues a new operation identity for each call, and the click binding at `:4959–4962` calls it directly. A rapid double submission can therefore create two projects. Disable repeated submission while the exact operation is pending and retain its identity for uncertain retries. The successful POST path also clears the form and shows an unqualified success toast when project-list refresh returns false. Say that creation succeeded but the list could not refresh, preserve the returned ID and offer Retry/Go to project; do not ask the user to create it again. Acceptance: delayed double-click produces one project; failed acknowledgement and failed follow-up refresh recover without duplicate creation. No duplicate was created during this audit.

**D30 · P2 · Member list can describe the previous project during a switch — Source.** `access.js:362–384` changes the selected project without clearing `members`; `:427–482` replaces them only after loading. Show a loading state or explicitly scope the retained list to its old project; never present A's names as B's members. Preserve existing disabled controls during refresh. Acceptance: hold B's member read, switch A → B, then fail it; old names never appear as B's current membership and Retry is available.

**D31 · P2 · Removing access and transferring ownership need a clear consequence — Source / UX proposal.** Member buttons (`access.js:404–409,726–741`) invoke Remove or owner-transfer immediately (`:650–674`). Add a focused confirmation naming the person, project and actual ownership effect; Cancel sends no request. Avoid blanket confirmations for routine task edits. Verify the last-Owner protection, current-user effects and stale membership revision. This audit did not execute any membership change.

**D32 · P2 · Initialize settings visibility before access loading — Check.** `access.js:293–302` hides admin-only Calendar/Allowance sections, but non-admin refresh calls it after `/access` resolves (`:511–525`), and `init()` does not apply it first (`:677–680`). HTML supplies the tabs/panels (`crm-admin.html:1412,1431,1462`). Refresh already disables several inputs, so this is not evidence of successful unauthorized writes. Verify delayed initialization and ensure inappropriate tabs/controls stay hidden or explicitly unavailable from the first paint; server authorization remains controlling.

**D33 · P2 · Allowance override has no Use default action — Source / feature gap.** `access.js:175,233` renders inherited values as Default; `:613–621` accepts only a numeric override and starts an inherited account's prompt at 5.00. The inspected server update requires a numeric allowance (`access-service.js:585–594,1102–1128`). If inheritance is intended to be reversible, add an explicit Use default contract in both client and server, with the existing revision/permission guards. Do not merely send null to the current API.
