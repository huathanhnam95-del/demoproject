**Status**: Active handoff reference

## 1. Why This Exists

This document explains the whole web app at takeover depth: the learner practice page, the admin CRM, the runtime architecture, the data model, the API contracts, the major workflows, the safety rules, and the verification entry points.

The project is a Firebase-backed vanilla JavaScript web app with a Node/Express local server, Firebase Cloud Functions in production, optional Python audio services, and a large amount of static learner content.

## 2. Mental Model

The product has two major systems:

1. **Practice app**: learner-facing English/PTE practice surface at `/`, backed by `public/index.html`, `public/script.js`, mode-specific JS files, local/static question banks, Firebase Auth/Firestore, and server-side AI/scoring helpers.
2. **CRM/admin app**: operations-facing teaching/business system at `/crm-admin.html`, backed by `public/crm-admin.*`, `public/js/crm/*.js`, Firestore `crm*` collections, and admin/teacher APIs.

The practice app and CRM are connected through:

- Firebase users and CRM student identity linking.
- Entrance tests generated by CRM and completed by learners.
- Classroom/student entitlements that control student status and practice-attempt retention.
- Reporting/admin views that summarize learner activity and read-aloud usage.

## 4. Runtime Topology

### Local Development

- Start point: `server.js`.
- App factory: `src/server/app.js`.
- Default local app URL: `https://localhost:8443` when local certs exist; otherwise HTTP on the selected port.
- Emulator guard: local startup fails closed unless Firebase emulator env vars are present, or `ALLOW_PROD_FIREBASE=1` is explicitly set.
- Recommended local command: `npm run dev` because it starts emulators and sets local emulator env vars before running `node server.js`.
- Emulator ports from `firebase.json`:
  - Firestore: `localhost:8080`
  - Auth: `localhost:9099`
  - Functions: `localhost:5001`
  - Storage: `localhost:9199`
  - Emulator UI: `localhost:4000`

### Production

- Firebase Hosting serves `public/`.
- `firebase.json` rewrites `/api/**` to the Cloud Function `api`.
- Function entrypoint: `functions/src/index.js`.
- Production API app: `functions/src/apiApp.js`.
- Functions runtime: Node.js 20.
- Hosting/functions predeploy builds the read-aloud connected-speech index through `scripts/read-aloud/build-connected-speech-index.js`.

### Optional Local Services

- Pronunciation/Praat and audio analysis helpers live under `backend/` and `backend/local_server/`.
- Extended mode keyword/paraphrase support can use the Python Flask backend.
- Ollama is used by the essay assessment route when available locally.

## 6. Learner Practice App

### Shell Responsibilities

`public/index.html` holds the static DOM for:

- Auth/login/signup overlays.
- Account profile and skill dashboard.
- Practice launcher and mode panels.
- Progress panel and vocabulary panel.
- SRS, reading journey, and mode-specific containers.

`public/script.js` owns:

- Global app state and launcher state.
- Practice skill grouping and mode switching.
- Practice scope (`english` / `pte`) via `PracticeScopeManager`.
- Deep-link routing with `/practice/{skill}/{mode}[/{questionId}]`.
- Current mode indicator, card rendering, active-mode lifecycle, and tutorial integration.
- Attempt assist metadata and active-skill usage.

### Practice Scope Rules

- `english` is the default scope.
- `pte` changes labels, skill grouping, and visible modes without changing mode engines.
- Scope persists to `localStorage['practiceScope']`.
- If a user switches into a scope where the active mode is hidden, the launcher auto-switches to a safe visible mode.
- Current PTE allowlist is in `PRACTICE_SCOPE_CONFIG[SCOPE_PTE].visibleModes`.
- `asq` has a PTE label override but is not currently in the PTE visible set; add it to that set if the product should expose Answer Short Question as a launcher card.

## 7. Practice Progress, Scoring, and Retention

### Progression

- Cloud Functions expose callable scoring/economy operations from `functions/src/index.js`:
  - `submitAttempt`
  - `purchaseItem`
  - `purchaseSkill`
  - `useActiveSkill`
  - `syncProgressionUnlocks`
  - `migrateUserCoins`
  - `assessWriting`
- User-owned Firestore profile fields include level selection, practice stats, unlocked modes, SRS bonus, and non-sensitive client-writable metadata.
- Server-owned fields include points/currency, points history, purchases, and authoritative scoring outcomes.

### SRS and Vocabulary

- SRS UI: `public/srs-review.js`, `public/srs-review.css`, `public/srs-scheduler.js`.
- SRS model helpers: `public/js/srs-card-model.js`, `public/js/srs-storage.js`, `public/js/srs-constants.js`.
- Vocabulary panel: `public/vocab-book.js`.
- Authenticated data lives under `users/{uid}/srs_cards`, `users/{uid}/vocabularyBook`, and related subcollections.
- Guest/local loops use localStorage where supported.

### Speaking Practice Attempts

- Server routes: `functions/src/routes/practice-attempts.js` and `functions/src/routes/shared-practice-attempts.js`.
- Local Express mounts the same routers under `/api/practice-attempts` and `/api/shared/practice-attempts`.
- Attempt flow:
  1. `POST /api/practice-attempts/prepare`
  2. Upload audio to the signed/validated Storage path.
  3. `POST /api/practice-attempts/:attemptId/complete`
  4. Optional bookmark/share/feedback operations.
- Retention:
  - Active students keep attempts permanently.
  - Logged-in non-students default to temporary retention unless bookmarked.
  - Non-student bookmarks are capped.
  - Promotion/reconciliation scheduled jobs update retention when CRM access changes.
- Scheduled jobs from `functions/src/index.js`:
  - `speakingAttemptCleanupRunner`
  - `practiceAccessReconcileRunner`
  - `practiceAccessPromotionRunner`

## 10. Firebase Security and Storage

### Firestore Rules

`firestore.rules` enforces:

- Users can read/write only safe fields under their own `users/{uid}` document.
- Progress, SRS, writing history, vocabulary, watch progress, and note progress are owner-scoped.
- Points history and purchases are server-only writes.
- `contentItems` are public read and Admin SDK write-only.
- Watch/take-notes content is public read and admin write.
- CRM students are readable by admins or linked users; writes are admin-only.
- Classroom data is readable by admins or student-claimed users; writes are admin-only.
- Speaking attempts, shares, counters, events, access jobs are server-owned.

### Storage Rules

`storage.rules` enforces:

- Classroom uploads under `uploads/{classId}/{workId}/{uid}/...` are student-owner write/read and admin read.
- Practice attempt audio must be `student.wav`, owner-authenticated, WAV-like content, size-limited, and tied to an awaiting-upload Firestore attempt.
- Teacher/admin feedback audio is similarly size/type/path constrained and server-mediated for reads.

## 13. Known Product/Engineering Gaps

Confirmed by existing CRM audit docs:

- Facebook/Messenger conversation context is not modeled beyond source/contact fields.
- Live class hosting is not a full built-in meeting product; live-session records and links exist, but hosting itself is external/manual.
- Zoom link management is partial and should not be assumed to be a complete meeting workflow.
- Attendance does not automatically prove or close a hosted class.
- Homework return/revision/resubmission exists in parts but is not a complete polished end-to-end teaching loop.
- Teacher feedback persistence exists for speaking attempts, but not every admin UI path is equally mature.
- Reading Journey is hidden/prototype-gated and should not be promoted without passing its promotion gates.

## 14. Development Rules for Takeover

- Treat `docs/specs/` as the product truth before writing code.
- Keep local development isolated from production Firebase unless intentionally overridden.
- Keep Cloud Function routes and local Express mirrors in parity when adding production API endpoints.
- Keep CRM collection names centralized through `functions/src/crm/collections.js`.
- Do not move sensitive writes client-side; prefer server-authoritative routes/functions.
- Add or update targeted tests near the feature being changed before relying on broad suites.
- For browser verification, prefer the existing `tests/browser/*` harnesses rather than ad-hoc manual clicking.
- Update `docs/specs/product.md` and this document when adding a new major mode, CRM workspace, data collection, API family, or scheduled job.
