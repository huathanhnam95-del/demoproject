#### Patch A: The Collision-Proof Loop (Backend)
**File:** `functions/src/studentIdentity.js`
**Risk:** High. As user count grows, `Math.random` will eventually generate a duplicate code, causing account hijacking.
**Fix:** Wrap generation in a uniqueness check.

```javascript
// REPLACE existing generateClassCode function
const generateClassCode = async () => {
  const chars = 'ABCDEFGHJKLMNPQRSTUVWXYZ23456789'; // No I, 1, O, 0
  let code = '';
  let isUnique = false;
  let attempts = 0;

  while (!isUnique && attempts < 5) {
    code = '';
    for (let i = 0; i < 6; i++) {
      code += chars.charAt(Math.floor(Math.random() * chars.length));
    }
    
    // Check DB for collision
    const snapshot = await db.collection('crmStudents').where('class_code', '==', code).get();
    if (snapshot.empty) {
      isUnique = true;
    }
    attempts++;
  }

  if (!isUnique) throw new Error('Failed to generate unique class code after 5 attempts.');
  return code;
};
```

### 1. Storage Rules: The "Free Hosting" Exploit
**Severity: HIGH**
**Location:** `storage.rules`

```javascript
match /uploads/{classId}/{workId}/{uid}/{allPaths=**} {
  // Students can read/write their own submissions
  allow read, write: if request.auth != null && request.auth.uid == uid;
}
```

**The Flaw:**
You are allowing **ANY** authenticated user (including anonymous logins if enabled, or just a standard free user) to upload files to your storage bucket.
*   **The Attack:** I script a bot to authenticate and upload 500GB of garbage data to `/uploads/fake-class/fake-work/my-uid/garbage.dat`.
*   **The Check:** You only check `uid == uid`. You **DO NOT** check if the user is actually a student, or if they are in a class.
*   **The Fix:** You must enforce the `isStudent` claim in the rules.

```javascript
allow write: if request.auth != null 
             && request.auth.uid == uid 
             && request.auth.token.isStudent == true; // <--- ADD THIS
```
*Why?* Because we are running a school, not a file locker service.

### 2. Firestore Rules: The "DB Spam" Exploit
**Severity: MEDIUM**

### 3. Identity Merging: The "Russian Roulette" Bug
**Severity: CRITICAL**
**Location:** `functions/src/studentIdentity.js` (Implied from Council Review)

**The Flaw:**
The Council review noted that `generateClassCode` creates a random string but **does not guarantee uniqueness** via a database transaction or loop.
*   **The Risk:** `claimProfile` uses `.limit(1)`.
*   **The Scenario:**
    1.  System generates Code `ABC123` for Student A.
    2.  System generates Code `ABC123` for Student B (Birthday Paradox makes this happen sooner than you think).
    3.  User X enters `ABC123`.
    4.  Firestore returns Student A (arbitrarily).
    5.  User X claims Student A.
    6.  **Student B is now unreachable and User X has the wrong identity.**
*   **The Demand:** You **MUST** implement a collision-check loop in the generation logic. If you deploy V1.5.0 without this, you are deploying a data corruption bug.
